# Специфікація проекту: RAG-асистент для студентів СумДУ

> **Версія:** 1.0
> **Дата:** 2026-02-05
> **Статус:** Draft

---

## 1. Огляд проекту

### 1.1 Призначення
Консультаційний асистент для студентів Сумського державного університету, який надає відповіді на питання щодо нормативних документів університету з використанням RAG (Retrieval-Augmented Generation) підходу.

### 1.2 Ключові можливості
- **Управління документами**: завантаження, редагування, видалення нормативних документів
- **Інтелектуальний пошук**: семантичний пошук по чанках документів через векторну базу
- **Відповіді на питання**: генерація відповідей на основі релевантних фрагментів документів

## 2. Цілі проекту

### 2.1 Бізнес-цілі
| ID | Ціль | Метрика успіху |
|----|------|----------------|
| G1 | Зменшити навантаження на адміністрацію | Автоматизація 70%+ типових питань |
| G2 | Покращити доступ студентів до інформації | Час отримання відповіді < 5 сек |
| G3 | Централізувати нормативну базу | Єдине джерело правди для документів |

### 2.2 Технічні цілі
| ID | Ціль | Критерій |
|----|------|----------|
| T1 | RESTful API для управління документами | CRUD операції через FastAPI |
| T2 | Векторний пошук по документах | pgvector similarity search |
| T3 | Чанкування та індексація документів | Автоматичний парсинг через markitdown |
| T5 | Локальні embeddings | Ollama + multilingual-e5-large |
| T6 | Генерація відповідей | Groq API |
| T4 | Масштабованість | Модульна архітектура |

## 3. Функціональні вимоги

### 3.1 API Документів
```
POST   /api/v1/documents          # Завантажити документ
GET    /api/v1/documents          # Список документів
GET    /api/v1/documents/{id}     # Отримати документ
PUT    /api/v1/documents/{id}     # Оновити документ
DELETE /api/v1/documents/{id}     # Видалити документ
```

### 3.2 API Питань
```
POST   /api/v1/questions          # Задати питання
GET    /api/v1/questions/history  # Історія питань (опційно)
```

### 3.3 API Чанків (внутрішній)
```
GET    /api/v1/chunks             # Пошук чанків
GET    /api/v1/chunks/{id}        # Отримати чанк
```

## 4. Структура даних

### 4.1 Таблиця `documents`
| Поле | Тип | Опис |
|------|-----|------|
| id | UUID | Унікальний ідентифікатор |
| title | VARCHAR(255) | Назва документа |
| content | TEXT | Оригінальний текст |
| source_file | VARCHAR(255) | Ім'я файлу джерела |
| doc_type | VARCHAR(50) | Тип документа (положення, наказ, тощо) |
| created_at | TIMESTAMP | Дата створення |
| updated_at | TIMESTAMP | Дата оновлення |

### 4.2 Таблиця `chunks`
| Поле | Тип | Опис |
|------|-----|------|
| id | UUID | Унікальний ідентифікатор |
| document_id | UUID (FK) | Посилання на документ |
| content | TEXT | Текст чанка |
| embedding | VECTOR(1024) | Векторне представлення |
| chunk_index | INTEGER | Порядковий номер чанка |
| metadata | JSONB | Додаткові метадані |
| created_at | TIMESTAMP | Дата створення |

## 7. Обмеження (Constraints)

### 7.1 Технічні обмеження
| ID | Обмеження | Обґрунтування |
|----|-----------|---------------|
| C1 | PostgreSQL як єдина СУБД | Вимога проекту + pgvector |
| C2 | Розмір чанка: 500-1000 токенів | Оптимальний баланс контексту |
| C3 | Embedding dimension: 1024 | multilingual-e5-large-instruct |
| C6 | Ollama має бути запущена локально | Для генерації embeddings |
| C7 | Groq API ключ обов'язковий | Для генерації відповідей |
| C4 | Логування через модуль `logging` | Заборона `print()` |
| C5 | Всі винятки повинні логуватися | Вимога code style |

### 7.2 Обмеження безпеки
| ID | Обмеження |
|----|-----------|
| S1 | API ключі тільки через змінні середовища |
| S2 | Валідація всіх вхідних даних через Pydantic |
| S3 | SQL injection prevention через ORM |

### 7.3 Обмеження scope (Out of Scope)
- ❌ Автентифікація користувачів (MVP)
- ❌ Веб-інтерфейс користувача
- ❌ Мультитенантність
- ❌ Кешування відповідей
- ❌ Rate limiting
